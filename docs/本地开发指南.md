# Lumen 本地开发指南

> 面向 V0.1 的实现说明：如何在本地跑起来、验证什么、以及代码在哪里。

## 1. 快速开始

```bash
# 1. 准备环境（创建 Python venv、安装 pyobjc、拉取 Go 依赖）
make setup

# 2. 一键跑通端到端联调（假事件 → Session → mock DeepSeek）
make e2e

# 3. 运行全部测试与检查
make check
```

`make e2e` 不需要任何真实密钥，也不会产生 DeepSeek 费用：它启动一个 mock
模型服务，并验证发往模型的内容不含路径、凭证或原始事件。

## 2. 本地手动跑一遍

### 2.1 启动服务端

```bash
cd server
LUMEN_LISTEN_ADDR=127.0.0.1:8787 \
LUMEN_DB_PATH=./data/lumen.db \
LUMEN_ENROLLMENT_TOKEN=dev-enroll-token \
LUMEN_ADMIN_TOKEN=dev-admin-token \
go run ./cmd/lumen-server
```

此时没有配置 `LUMEN_DEEPSEEK_API_KEY`，AI 能力自动关闭，但采集、同步、Session
和查询全部可用——这是有意的降级设计。

### 2.2 注册采集端

```bash
cd desktop
.venv/bin/python -m lumen_desktop init-config     # 生成 ~/.lumen/config.json
# 修改 config.json 里的 server_url 指向本地服务端
.venv/bin/python -m lumen_desktop register --token dev-enroll-token
```

device_token 会存入 macOS 钥匙串，不会写入任何文件。

### 2.3 运行采集

```bash
.venv/bin/python -m lumen_desktop run       # 前台运行，Ctrl-C 退出
.venv/bin/python -m lumen_desktop status    # 另一个终端查看状态
.venv/bin/python -m lumen_desktop events    # 查看实际会上传什么
.venv/bin/python -m lumen_desktop pause     # 暂停采集
.venv/bin/python -m lumen_desktop resume    # 恢复采集
```

### 2.4 生成一份总结

```bash
curl -X POST "http://127.0.0.1:8787/api/v1/summaries/daily/generate?date=$(date +%F)" \
  -H "Authorization: Bearer dev-admin-token"
```

服务端会自动重算当天的 Session，再用它们生成总结。

## 4. 几个关键设计决定

### 为什么 Session ID 是内容派生的而不是随机 ULID

Session 每次重算都会重新生成。如果 ID 用随机值，那么：

- 总结里保存的 `evidence_session_ids` 下次重算就全部失效；
- `input_hash` 相同的判断永远不成立，会反复调用模型花钱。

因此 Session ID 由 `日期 + 项目 + 起止时间 + 算法版本` 做 SHA-256 派生。
只要这段时间的工作内容没变，重算就得到同一个 ID。

### 为什么 Git 归因窗口只有 15 分钟

用 Git 事件给窗口活动补项目归属本质上是一种**推测**。窗口设得太宽，会把
「提交前后刚好在浏览器上看网页」也算进这个项目，导致总结失真。

产品原则是「无法可靠识别就不猜测」，所以归因窗口刻意设小，
宁可少归因也不乱归因。

> **注意区分**：内部标记 `unclassified` 只用于存储、日志与 API。
> 给用户看的文案统一走 `feishu.ProjectDisplayName` / `ai.ProjectDisplayName`
> 转成「暂未识别项目」——用户看到 `unclassified` 只会以为系统出错了。

### 为什么 Session 的切断点是「离开区间」的起点

这是真机踩过的坑，值得写清楚。

`idle.state` 描述的是**一段状态区间**：`timestamp` 是区间开始时刻，
`data.duration_seconds` 是区间长度（缺省表示区间尚未结束）。
`idle` 区间的起点取「最后一次输入」的时刻，`locked` 区间起点是锁屏时刻。

服务端据此切断 Session：

- `locked` 一律切断；
- `idle` 只有持续 ≥ 8 分钟才切断（短暂 idle 可能只是在看视频）；
- 切断点取区间**开始**——用户真正离开的时刻，不是发现离开、更不是回来的时刻；
- 离开区间内的窗口活动一律裁剪掉。锁屏期间不可能有工作，无论事件是真是假。

早期实现写的是「上一段状态 + 状态变化时刻」，服务端又按
`timestamp + duration` 取区间结尾，方向反了：锁屏 12 小时被算成工作，
22:30 的总结因此明显偏高。

### 历史脏数据怎么处理

**不删除原始事件。** 重算时按 `schema_version` 区分新旧语义，并忽略
`loginwindow` 这类系统伪应用的窗口活动：

| `data.schema_version` | 语义 | 区间 |
| --- | --- | --- |
| `>= 2` | 新语义 | `[timestamp, timestamp + duration_seconds)` |
| 缺省 | 旧语义 | `[timestamp - duration_seconds, timestamp]` |

重算某天会向前多看 24 小时（跨夜离开区间的起点可能在昨天），
但只把「开始时刻落在当天」的结果写回，避免污染相邻日期。
算法版本 `rules-v2` 会让 Session ID 重新派生，旧的脏 Session 自动被替换。

运维入口：

```bash
# 单日重算
curl -X POST "http://<server>:8787/api/v1/sessions/rebuild?date=2026-09-17" \
    -H "Authorization: Bearer <ADMIN_TOKEN>"

# 区间重算（最多 92 天）
curl -X POST "http://<server>:8787/api/v1/sessions/rebuild?from=2026-09-17&to=2026-09-18" \
    -H "Authorization: Bearer <ADMIN_TOKEN>"
```

### 为什么图片和表格的字段用 allowlist 而不是 blocklist

上传字段是通过 `ALLOWED_CONTEXT_KEYS` / `ALLOWED_DATA_KEYS` 逐项构造的，
而不是「先序列化再删掉敏感字段」。这样将来即使传感器对象里多了一个字段，
也不会因为忘记加进黑名单就泄露出去。

### 为什么模型失败不影响其他功能

总结调用、飞书推送、AI 问答三者都是「尽力而为」：

- 模型失败 → 总结标记 `failed`，事件和 Session 照常可查；
- 飞书失败 → 总结已保存，只标记投递失败，可补发；
- 预算用尽 → 问答降级为确定性摘要，仍然带证据。

### 为什么问答不做关键词匹配

改一种说法就要改代码，是把模型能做的事交给了 if-else，而且真实说法永远比
正则写得出的多。所以默认入口是模型出计划、代码只审批：

```text
用户消息 + Profile + 对话状态 + 能力目录 → AgentPlan
  → Policy Gate（工具白名单 / 参数 schema / 只读 / 调用数上限）
  → 只读 Capability → 事实回交模型 → Answer + 支持等级 + 来源校验
```

新增能力的成本是加一个 Capability（名字、参数、只读），模型自动学会用它，
不需要给代码加分支，也不需要写新的关键词。`ParseQuery` 那套只作为模型
完全不可用时的最小兜底保留。

## 5. 测试策略

```bash
make test-server     # Go 单元与集成测试
make test-desktop    # Python 测试
make e2e             # 端到端联调
```

重点覆盖的场景：

- **幂等**：同一批事件上报 3 次，服务端仍只有一份；
- **部分失败**：单条被拒绝时其余事件仍成功；
- **隐私**：剪贴板、截图、源代码、绝对路径、窗口标题字段全部被拒；
- **Session 规则**：3 分钟合并、10 分钟 idle 切断、项目切换不合并、未识别不猜测；
- **真实时序**（`desktop/tests/test_idle_lifecycle.py`、
  `server/internal/sessions/engine_away_test.go`）：工作 → idle 超 8 分钟 →
  锁屏数小时 → 解锁；断言锁屏期间没有工作记录、Session 在离开时结束、
  跨日不污染、恢复后能重新采集、系统睡眠不算活跃；
- **历史脏数据**：旧语义的 `idle.state`（`timestamp` 是区间结束）与
  `loginwindow` 假活动在重算时被正确处理，原始事件不删除；
- **降级**：模型不可用、飞书不可用、预算用尽时的行为；
- **数据最小化**：发给模型的内容经过扫描，确认无路径、凭证、URL；
- **用户文案**：回复与总结中不出现 `unclassified`、内部 Session ID 等工程术语。

## 6. 故障排查

| 现象 | 先查什么 |
| --- | --- |
| 采集端一直没有事件 | `lumen-desktop doctor`，确认 pyobjc 与辅助功能权限 |
| 窗口标题读不到 | 正常降级行为，只记录应用名；需要标题请授予辅助功能权限 |
| 事件卡在本地 | `lumen-desktop status` 看待同步数量；确认服务端可达与 token 有效 |
| 总结一直是 failed | 查看 `daily_summaries.error_code`，再查 DeepSeek key、余额、模型名 |
| 数据库变大 | 检查 `data/` 下 WAL 文件；服务端每天凌晨会 checkpoint 与清理 |
| 工作总时长明显偏高 | 先看 `idle.state` 的 `schema_version` 与子应用清单，再按上文重算 Session |
| 磁盘告警 | 减小 `LUMEN_EVENT_RETENTION_DAYS`，确认备份保留份数 |
