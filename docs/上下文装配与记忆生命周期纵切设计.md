# 上下文装配与记忆生命周期纵切设计

> 状态：已实现（本地，未部署）。本文档先于实现编写，是实现与验收的对照基准。
> 范围：只做「Context Assembler + 记忆生命周期」这一条纵切。不含部署、不含飞书确认交互、不重构工具层。

## 0. 问题与目标

当前每轮回答的上下文是散着拼的：Agent 直接读 `conversation_states`（`loadState`），
提示词各阶段各自渲染，身份块重复出现在系统提示里；候选记忆与已确认信息之间
没有生命周期（候选永远停在 candidate，没有任何确认入口）。本纵切把「送进模型的
每一轮上下文」收敛到一个**受预算、可解释、可纠错**的装配器：

- 每轮一个 `ContextBundle`：trusted_context（只由代码生成）+ untrusted_evidence（带来源与限额）。
- Planner 与 Synthesizer 接收**同一个** Bundle 对象，不再各自查询存储。
- 候选记忆永远不进模型上下文；只有经用户确认的偏好类记忆通过独立的
  UserProfile 读模型进入下一轮。
- 本地管理 API 负责确认/拒绝，全部有审计。

## 1. 分层与依赖

```
feishu.QAService / api / initiative        ← 装配根：构造 Assembler，每轮传 Bundle
        │
assistant.Agent                           ← 编排：只消费 Bundle，不再 loadState
        │
contextassembler（新包）                   ← 本纵切的核心边界
  Assembler.Assemble(ctx, Request) *Bundle
  Bundle（Trusted + Evidence + Budget + 截断元信息 + 渲染）
        │
storage.Store                             ← 只被 Assembler 与 profile.Service 调用
```

依赖规则：

1. `assistant.Agent` **不允许**直接为拼上下文读 storage。原 `loadState` 迁入
   Assembler；`saveState`（写上一轮状态）保留在 Agent——它是轮后记账，不是装配。
2. `contextassembler` 只依赖 `temporal`、`identity`、`storage`、`tooling`；
   `assistant` 依赖 `contextassembler`；反向不存在依赖。
3. `profile` 包（记忆生命周期服务）依赖 `storage`；被 `api` 调用；
   与 `assistant`/`tooling` 无依赖。工具层只多一个 `key` 参数，不重构。
4. 模型只做语义判断；预算、截断、谁进上下文，全部由代码决定。

## 2. 数据模型与状态机

### 2.1 ContextBundle（每轮一个）

```
Request{UserID, Temporal, UserText}
    │ Assemble（唯一入口）
    ▼
Bundle{
  TurnSource "u_<ulid>"          // 代码生成，模型不可伪造
  Trusted{Temporal, Identity, ProfileEntries, Summary}
  Evidence []EvidenceItem        // {Source, Kind, Body}
  UserText string                // 清洗后
  Truncations []string           // 截断元信息（永不静默截断）
}
```

- **Trusted**（trusted_context 块）：
  - **代码控制的部分**：块结构（开闭标签、字段行、段落顺序）、可信时间
    （Temporal，时钟读数）、助手身份（Identity，配置）——这三样是代码生成的；
  - **动态值部分**：已确认信息（ProfileEntries 的 key/value）与会话摘要
    （Summary 三字段）的**内容**最终来自用户原话/模型输出，经用户确认选择。
    它们**不是**"代码生成事实"，只是被代码归属（确认过来源与槽位）后
    **编码嵌入**的数据：渲染前压平空白 + XML 转义（TemporalGuard 纠正要求
    同样编码），因此无法闭合块、伪造字段行或注入伪指令（攻击回归测试见
    `trusted_block_attack_test.go`）；
- **Evidence**：`Kind=recent_turn`（近期有限轮次，来源 `conversation`）与
  `Kind=tool_result / denied`（本轮工具事实，来源 `tool:<名>`）。全部转义后进各自
  分隔块。近期轮次取自 conversations 表最近 N 轮的用户话与回答，**不属于 trusted**。

### 2.2 记忆状态机

```
            confirm(candidate_id)             confirm(candidate_id)
candidate ────────────────────────▶ confirmed ◀────────── （幂等：不重复计版本）
   │  ▲
   │  └─ 拒绝后再确认 → 409（拒绝是终态，撤销不在本版本）
   ▼
rejected ──▶ 不可进入 Profile；再拒绝幂等
```

- **确认是单个原子操作**（`storage.ConfirmMemoryCandidate`）：条件状态转换
  （`UPDATE … WHERE status='candidate'`）+ Profile 当前值投影 + 版本历史
  在**同一个事务**里。任何一步失败整体回滚——候选仍是 candidate、读模型与
  历史不动，不存在"confirmed 但没有投影"的半状态。
- **并发语义**：条件更新保证多个并发确认只有一个真正生效，其余幂等返回
  `already_confirmed`，version 只加一次；确认/拒绝并发时只有一个方向生效
  （条件更新 + 失败后重读裁决），互不覆盖。`RejectMemoryCandidate` 同为
  条件转换。
- 服务层（profile.Service）只做**不写库**的前置裁决：敏感内容检查、类别
  白名单、槽位 key 归一化（候选内容不可变，因此"先读后判再原子转换"
  没有 TOCTOU 窗口）。
- **审计失败策略**：`security_events` 是观测层，写入失败只记 WARN 日志，
  绝不回滚已提交的核心状态机；事务内的 `user_profile_history` 行才是
  与核心状态同生共死的权威审计。
- 原始候选**不改写**：确认/拒绝只追加决策列（`status/decided_at/decided_by/reject_reason`）。
- 确认（preference 类）→ UserProfile 读模型 `user_profile_entries`（每 (user_id,key) 一行当前值）
  + `user_profile_history`（追加式版本历史：action/previous_value/operator）。
- **纠正**：同一稳定 `key` 的候选再确认 → version+1 替换当前值，历史保留旧值；
  同一时刻每个 key 只有一个值注入，不存在两个矛盾值同时可见。
- fact/project 类也可确认（仅状态标记），**不**注入上下文——本版本只有偏好类入上下文。

### 2.3 迁移 v6

```sql
ALTER TABLE memory_candidates ADD COLUMN key TEXT NOT NULL DEFAULT '';
ALTER TABLE memory_candidates ADD COLUMN decided_at TEXT;
ALTER TABLE memory_candidates ADD COLUMN decided_by TEXT NOT NULL DEFAULT '';
ALTER TABLE memory_candidates ADD COLUMN reject_reason TEXT NOT NULL DEFAULT '';

CREATE TABLE user_profile_entries (     -- 读模型：当前值
  user_id TEXT NOT NULL, key TEXT NOT NULL, kind TEXT NOT NULL DEFAULT 'preference',
  value TEXT NOT NULL, version INTEGER NOT NULL DEFAULT 1,
  source_candidate_id TEXT NOT NULL DEFAULT '', source_ids_json TEXT NOT NULL DEFAULT '[]',
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
  PRIMARY KEY (user_id, key));
CREATE TABLE user_profile_history (     -- 版本历史（兼确认审计）
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL, key TEXT NOT NULL, version INTEGER NOT NULL,
  action TEXT NOT NULL,                 -- confirm_initial / confirm_replace
  candidate_id TEXT NOT NULL DEFAULT '', value TEXT NOT NULL,
  previous_value TEXT NOT NULL DEFAULT '', operator TEXT NOT NULL DEFAULT 'admin',
  created_at TEXT NOT NULL);
```

兼容：旧库候选 `key=''`，确认时落到 `general` 槽位；`user_profile_*` 新表从空开始，
Assembler 对空/缺失自然降级。conversations 表复用为近期轮次来源，不加表。

## 3. 上下文预算与截断顺序

`Budget`（可配置、可测试；默认值见 `DefaultBudget()`）：

| 段 | 上限（默认） | 说明 |
|---|---|---|
| Profile | 每条 200 runes × 最多 8 条 | 已确认信息，最高优先 |
| Summary | 300 runes | 会话摘要 |
| RecentTurns | 3 轮 × 每轮 400 runes，总 1200 | 近期轮次 |
| Evidence | 单工具 8000、合计 20000 | 工具事实（沿用既有限额） |
| Total | 30000 runes | 整包上限 |

截断顺序（超预算时**从低优先级开始丢**，逐条记录进 `Truncations`）：

```
Profile（最后才丢） > Summary > RecentTurns > Evidence（最先丢）
```

- 每段先按自身上限裁剪（单项裁剪标"已截断"）；
- 整包超限时：先丢 Evidence 尾部条目 → 再丢最早的 RecentTurns → 再缩 Summary →
  最后按条丢 Profile；
- 一切丢弃都写入 `Truncations`（如 `evidence: 超出整包预算，丢弃 2 条`），
  **绝不静默随机截断**。可通过环境变量调总预算与轮数：
  `LUMEN_CONTEXT_BUDGET_TOTAL`、`LUMEN_CONTEXT_RECENT_TURNS`。

## 4. 隐私边界

1. **候选不可读入上下文**：Assembler 只读 `user_profile_entries`（确认投影）、
   `conversation_states`、`conversations`；不出现对 `memory_candidates` 的任何读取。
   测试断言候选正文不出现在任何提示词里。
2. **trusted_context 的结构由代码控制**：开闭标签、字段行与段落顺序只由
   `RenderTrusted` 生成。其中时间与身份是代码生成的事实（时钟/配置）；
   已确认信息、会话摘要、纠正要求三类**动态值**的内容来自用户/模型，
   渲染前压平空白 + XML 转义后嵌入——它们无法闭合 `</trusted_context>`、
   另起字段行（换行被压平）、伪造属性（块内无属性）或注入伪指令，
   只能作为被编码的数据出现。攻击回归：`trusted_block_attack_test.go`
   覆盖 `</trusted_context><user_message>`、`&`、换行分别进入
   Profile / ConversationState / correction 的场景，并断言"剥掉结构标签后
   块内无任何裸 < >"。用户文本进 `<user_message>`、工具返回进
   `<tool_data>`、近期轮次进 `<recent_turns>`、被拒步骤进 `<denied_steps>`，
   全部转义，无法提前闭合或覆盖 trusted 块。
3. **模型不能写 Profile**：唯一写入路径是管理 API 确认动作；工具层只能写候选，
   且偏好来源必须是代码生成的本轮来源（上一纵切已保证）。
4. **敏感内容拒绝确认**：确认前对内容做敏感信息检查（密码/密钥/token/凭证等），
   命中则拒绝确认并记录原因（security event + 返回原因），候选保持 candidate。
5. **拒绝不可见**：rejected 状态不产生任何 Profile 投影。
6. 审计：确认/拒绝写 `decided_by/decided_at/reject_reason`（候选行）+
   `user_profile_history`（确认）+ security event（管理动作），不记录候选正文以外的扩散。

## 5. 失败降级

| 失败点 | 行为 |
|---|---|
| 存储读失败（entries/state/turns 任一） | 该段置空 + `Truncations` 记录"读取失败已降级"，轮次继续 |
| 新库无任何已确认信息 | trusted 无该段（不是空占位） |
| Temporal 无效 | Assemble 仍返回 Bundle，但执行器 fail-closed 拒绝全部工具（上一纵切保证） |
| 确认目标不存在 | API 404 |
| 确认已确认 | 幂等 200（`already_confirmed`），不重复计版本 |
| 确认已拒绝 | 409（拒绝是终态） |
| 确认命中敏感内容 | 409 + 原因 + security event，候选保持 candidate |
| 确认的投影事务失败 | **整体回滚**：候选仍 candidate、读模型/历史无痕迹，API 500（失败注入测试覆盖） |
| 并发确认/拒绝竞争 | 条件更新裁决唯一方向：一个生效，其余幂等或 409（并发测试覆盖） |
| 审计（security_events）写失败 | 只记 WARN，不回滚核心状态（历史行才是权威审计），可观测 |
| 拒绝已确认 | 409（撤销确认不在本版本） |

## 6. 生命周期管理 API（管理令牌）

| 端点 | 说明 |
|---|---|
| `GET /api/v1/memory/candidates?status=&limit=` | 列候选/已确认/已拒绝 |
| `POST /api/v1/memory/confirm` `{"candidate_id"}` | 确认；幂等；preference 写 Profile |
| `POST /api/v1/memory/reject` `{"candidate_id","reason"}` | 拒绝；不可进入 Profile |
| `GET /api/v1/profile` | 查看已确认 UserProfile（含版本）与近期变更历史 |

不做飞书交互/UI；API + 手工验收（见 manual_acceptance）。

## 7. 工具层最小扩展

`save_memory_candidate` 新增可选参数 `key`（≤32 runes）：
**preference 类必填**（缺失即拒绝执行）——稳定槽位名（如"称呼/作息/沟通风格"），
纠正确认时替换同名槽位。fact/project 类可选。其余工具层不动。

## 8. 验收用例

P0：
1. 固定时钟下，Planner 与 Synthesizer 提示词中的 `<trusted_context>` 块**逐字节相同**
   （时间+身份+已确认信息+摘要），且两者不再各自读存储（fake store 计数）。
2. 预算截断次序：极小预算下按 Evidence→Turns→Summary→Profile 丢弃，
   `Truncations` 全程可解释。
3. 候选正文（candidate 状态）不出现在任何提示词。
4. 缺失存储/空表时自然降级，不 panic、不阻塞回答。

P1/P2：
5. 确认后下一轮可见：确认偏好 → 下一轮 planner/synth 提示词包含该条目（API 验收含端到端）。
6. 拒绝不可见：rejected 不出现在 Profile 与提示词。
7. 纠正：同 key 二次确认 version+1、替换当前值、历史保留旧值、单值注入。
8. 重复确认幂等：第二次确认无版本增长、无重复历史。
9. 敏感拒绝：含敏感内容候选确认被拒并记录原因。
10. 候选不泄露：保存候选后 GET /api/v1/profile 为空，直到确认。
11. 管理端点全部要求管理令牌；401/404/409 语义正确。

e2e：保存候选（mock 模型带 key）→ 管理确认 → 提问"你怎么称呼我"，
mock 模型从 trusted_context 读取已确认信息作答 → 回答包含确认值。

## 9. 明确非目标

- 不做飞书确认交互/任何 UI；不做候选自动晋升。
- 不做 key 的语义去重或同义合并（key 由模型给出、代码归一化）。
- 不做撤销确认/重新打开已拒绝候选。
- 不做 fact/project 类注入上下文；不做向量检索/长期记忆召回。
- 不重构既有工具层（除 `key` 参数）；不改主动关怀链路。
- 不部署、不提交、不推送（遵守当前任务约束）。
