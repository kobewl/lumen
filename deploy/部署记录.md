## 3. 为什么用"本地构建 + scp"而不是服务器拉取

服务器在国内，直连 Docker Hub 超时。已经在服务器配置了镜像加速器
（`/etc/docker/daemon.json`），但它只用于拉基础镜像。业务镜像在本地
交叉编译成 amd64 后压缩上传，8.7MB，比在服务器上传依赖更快也更可控。

## 4. 更新服务的标准流程

```bash
# 0. 确认仓库干净、检查全绿
make check

# 1. 构建新版本镜像（版本号递增；VERSION 会注入二进制，healthz 能报出版本）
cd /path/to/lumen
docker buildx build --platform linux/amd64 \
  --build-arg VERSION=0.1.8 \
  -t lumen-server:0.1.8 --load -f deploy/Dockerfile .

# 2. 部署前快照（重要：迁移不可逆，先留退路）
ssh lumen-vps 'sudo docker run --rm -v /var/lib/lumen:/data \
  -v /var/lib/lumen/predeploy-backups:/backup alpine:3.20 sh -c "
  apk add --no-cache sqlite >/dev/null 2>&1
  sqlite3 /data/lumen.db \".backup /backup/predeploy-0.1.8-\$(date +%Y%m%d-%H%M%S).db\""'

# 3. 导出并上传
docker save lumen-server:0.1.8 | gzip -9 > /tmp/lumen-0.1.8.tar.gz
scp /tmp/lumen-0.1.8.tar.gz lumen-vps:/tmp/

# 4. 服务器加载并切换
ssh lumen-vps '
  gunzip -c /tmp/lumen-0.1.8.tar.gz | docker load
  rm -f /tmp/lumen-0.1.8.tar.gz
  cd /opt/lumen
  cp docker-compose.yml /tmp/docker-compose.yml.bak-<旧版本>
  sed -i "s|lumen-server:0.1.7|lumen-server:0.1.8|" docker-compose.yml
  docker compose up -d
  sleep 6 && docker ps && docker logs lumen-server --tail 5
'

# 5. 确认版本与迁移（healthz 的 version 必须是新版本号）
ssh lumen-vps 'curl -s http://127.0.0.1:8787/api/v1/healthz'
```

**数据库迁移**：迁移在 `storage.Open` 时自动执行（`CREATE TABLE IF NOT EXISTS`，
按 `schema_migrations` 表跳过已应用的版本）。**迁移前一定要有快照**：
迁移会改写库，回滚镜像不会回滚 schema。

**回滚**：把 `sed` 的版本号改回旧版本，重新 `docker compose up -d` 即可。
镜像都还在本地，秒级回滚；但如果新版本带了 schema 迁移，
需要连同快照一起恢复（见 `predeploy-backups/`）。

## 10. 已知行为说明

### 锁屏与 idle 时间不算工作（2026-09-18 修复）

2026-09-17 的真机账目明显偏高：当天真实使用只有 ZCode 22.7 分钟 +
Tabbit 1.7 分钟，库里却记录了 674 分钟的 `loginwindow` 活动，
22:30 的总结因此把锁屏后的时间算成了约 2 小时工作。

根因有三处，已全部修复：

1. 采集端的 `idle.state` 写的是「上一段状态 + 状态变化时刻」，
   active→locked 时数据库里直到次日解锁才出现 locked 记录，Session 切断点严重滞后；
2. 锁屏后窗口传感器仍在继续采集，把 `loginwindow` 当成前台应用累计时长；
3. 服务端按 `timestamp + duration` 取切断点，方向反了（取到了 idle 结束之后）。

修复后的行为：

- `idle.state` 是状态区间：`timestamp` = 区间开始，`duration_seconds` = 区间长度，
  缺省表示区间未结束；`idle` 区间起点取「最后一次输入」的时刻；
- 锁屏 / idle 后窗口计时立即停止，恢复 active 后才重新开始；
  采集端与 Session 引擎各有一层防御，`loginwindow`、屏保、认证窗口永不计数；
- Session 切断点落在**用户离开的时刻**，离开区间内的活动一律裁剪。

重算历史数据（原始事件不删除）：

```bash
curl -X POST "http://127.0.0.1:8787/api/v1/sessions/rebuild?from=2026-09-17&to=2026-09-18" \
    -H "Authorization: Bearer $LUMEN_ADMIN_TOKEN"
```

规则版本升到 `rules-v2`，Session ID 会重新派生，旧的脏 Session 自动被替换。
重算后 2026-09-17 的工作时长应约为 24 分钟（ZCode + Tabbit），
不再出现 `loginwindow`。

采集端本身也需要更新到这一版代码并重启，否则会继续产生 `loginwindow`
假活动（服务端仍会在重算时忽略它们，但每天的实时统计会失真）。

### 为什么当前 Session 是「暂未识别项目」

采集端只上报应用名与时长，不上传窗口标题。项目归属来自两处：
配置里的项目白名单（窗口标题命中关键词）与附近 15 分钟内的 Git 提交。

日常在 ZCode 里工作时既有白名单命中也可能没有 Git 提交，
此时按设计标为未识别 —— 这是"宁可不说也不猜"的刻意选择，不是缺陷。
内部标记是 `unclassified`，但用户可见文案统一显示为「暂未识别项目」。
想让归属更准确，可以在 `~/.lumen/config.json` 的
`project_keywords` 里增加你常用应用标题中的项目关键词。

### 能查到什么、查不到什么（V0.1 边界）

记录范围只有**应用名和时长**，看不到窗口标题、网页内容、代码或剪贴板。
所以：

- 能回答：今天/昨天/某个项目用了哪些应用、各多久、有哪些 Git 提交；
- 不能回答：具体写了什么功能、完成了什么任务。应用时长不等于任务内容，
  证据不足时总结会明确写「只有应用与时长记录，看不出具体做了什么」。

## 11. 2026-09-18：AI-first Agent Runtime 与任务摘要（0.1.8）

### 这次改了什么

问答链路从「正则判意图 → Go switch → 固定分支」换成 AI-first 编排：
模型生成计划 → Policy Gate 审批 → 执行只读能力 → 模型合成回答 → 代码校验。
Go 代码里不再有关键词路由。同时新增第三类数据源 `agent.task_summary`：
专业 Agent（如 ZCode）通过采集端 CLI 提交结构化任务摘要，
经本地 allowlist 与敏感校验后进离线队列，服务端幂等入库，
再由只读能力 `get_task_summaries` 提供给模型。

### 部署要点

| 项 | 值 |
| --- | --- |
| 版本 | `0.1.7` → `0.1.8` |
| 库迁移 | v1 → v3（迁移 2、3 为新增表，不改动既有表结构） |
| 影响面 | 只新增表与接口，不改动 `events` / `sessions` / `daily_summaries` |
| 部署前快照 | `/var/lib/lumen/predeploy-backups/predeploy-0.1.8-*.db` |
| 演练 | 迁移前先把生产库副本拉到本地跑过一遍，确认数据无损 |

### 关于版本号注入（本次新增）

`api.Version` 从常量改为变量，由 `deploy/Dockerfile` 通过
`--build-arg VERSION=0.1.8` 注入。此前 healthz 恒返回 `0.1.0`，
与实际运行的镜像版本对不上，升级后无法从接口确认线上版本。
现在构建时忘传会显示 `dev`，不会再谎报一个旧版本号。
